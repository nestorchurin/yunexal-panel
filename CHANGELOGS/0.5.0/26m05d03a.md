## Snapshot - 3.05.2026 - 0.0.0-snapshot-26m05d03a

### Storage policy lock: ext4 + prjquota only
- `src/handlers/create.rs`:
	- storage validation is now strict: only `ext4` mounts with `prjquota`/`prjjquota` are accepted for container storage
	- quota preflight (`/api/quota-check`) now reports ext4-only policy signals
	- removed legacy `api_xfs_check` alias route handler
- `src/handlers/admin.rs`:
	- storage mount discovery now only exposes ext4 block-device mounts
	- disk-format endpoint (`/api/admin/storage/change-fs`) now accepts only `ext4`
	- migration and disk-limit flows no longer branch into XFS/ZFS/Btrfs paths
- `src/host.rs`:
	- admin tool resolver now keeps only `mkfs.ext4` for filesystem formatting actions

### Quota enforcement cleanup
- `src/handlers/servers.rs`:
	- server deletion now clears ext4 project quota state via `remove_ext4_quota` before removing volume data
- `src/handlers/mod.rs`:
	- removed `/api/xfs-check` route registration (clients use `/api/quota-check`)
- `src/auth.rs`:
	- removed `/api/xfs-check` from admin permission path mapping

### Quota deletion bugfix
- `src/docker/quota.rs`:
	- `remove_ext4_quota(...)` now has fallback cleanup across all ext4 mounts with `prjquota`/`prjjquota`
	- this prevents stale project quota when volume path resolution fails during container deletion flows
- `src/handlers/admin.rs`:
	- storage migration now explicitly clears quota on the old source path right after old container recreation/removal
	- avoids leftover quota binding on source volumes when container identity changes

### Post-reboot permission stability fix
- `src/handlers/admin.rs`:
	- storage migration now preserves root volume directory owner/mode from source to target before recreate/start
	- added privileged `chown/chmod` normalization in migration pipeline to prevent target volume root becoming `root:root` after sudo `mkdir/rsync`
	- this reduces cases where containers fail to start after reboot or lose write access due host-path permission drift
